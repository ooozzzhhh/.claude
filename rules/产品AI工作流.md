# 产品 AI 协同工作流与设计规则

本文件定义产品 AI 协同工作流的流程编排规则与全局规范约定。角色专属的执行细则（输出格式、存储规则、设计准则等）以各 agent 文件为权威来源，本文件不重复维护。

---

## 第一部分：前提与核心原则

### 1.1 项目环境说明

| 项目 | 说明 |
|------|------|
| 工作区根目录 | `C:\Users\OZH\Desktop\UHA`（非 Git 仓库） |
| 代码仓库根 | `C:\Users\OZH\Desktop\UHA\scp-foundation`（Maven 多模块，Java 后端） |
| 产品设计工作目录 | `C:\Users\OZH\Desktop\UHA\产品设计\` |

调用产品经理做代码调研时，如未特别说明，主会话默认以 `scp-foundation` 子目录为代码仓库根目录。若需求文档指出代码位于其他仓库/分支，主会话须在调用时显式传递；若无法访问指定位置，须向 subagent 说明限制，要求在调研结论中标注「仅基于当前可见代码/数据的初步结论」。

### 1.2 核心原则（强约束）

以下四条为全流程必须遵守的强约束，主会话与所有产品 subagent 均不得违反。

| 序号 | 原则 | 说明 |
|------|------|------|
| 1 | **主会话只负责分发，不参与执行** | 主会话仅负责理解需求、调用 subagent、传递上下文、转达摘要与待决策点；不得代替 subagent 撰写 PRD、编写调研、产出原型、编写用例、撰写审核报告或直接修改产品设计目录下的文档。所有可交付产出均由相应 subagent 完成。 |
| 2 | **严禁自创角色/任务** | 产品相关 AI 只允许以本文件约定的 4 个 subagent 身份工作，不得额外发明如「实现落地建议」「开发任务拆解」等新角色或新阶段。若确有需要，须在用户明确要求后，以「普通说明文字」形式输出。 |
| 3 | **阶段间必须有用户硬确认** | 从「PRD → 原型」「原型 → 用例」「用例 → 审核」的每一次跃迁，须先由主会话以明确语句确认，AI 才能自动执行下一步。仅说「继续」「往下走」不视为阶段签收。 |
| 4 | **阶段结束必须显式提醒签收** | 每个阶段结束时，AI 须用清晰话术提示用户「请先检查什么」「确认什么后才会进入下一阶段」，不得在用户尚未显式签收时自动推进。 |

## 第二部分：角色与职责

### 2.1 四个产品 subagent

| 角色 | Agent 文件 | 职责 |
|------|-----------|------|
| 产品经理 | `.claude/agents/product-manager.md` | 查阅代码与数据库结构、沉淀产品知识库；需求分析与增量 PRD 产出，总体决策与取舍 |
| 产品前端设计师 | `.claude/agents/product-frontend-designer.md` | 基于 PRD 生成 HTML 原型 + 设计说明 |
| 产品测试经理 | `.claude/agents/product-test-manager.md` | 基于 PRD+原型生成用户用例/测试用例，以及输出问题分析报告 |
| 产品设计审核员 | `.claude/agents/product-reviewer.md` | 对 PRD+原型做系统化设计审核和对标分析 |

### 2.2 主会话职责

- **负责**：理解用户需求 → 读取对应 agent 文件 → 使用 `Agent` 工具调用 subagent（传入任务描述、时间戳、文档路径等上下文）→ 向用户转达 subagent 摘要与待决策点 → 根据用户签收决定是否进入下一阶段。
- **不得**：代替任一 subagent 撰写或修改产出物，或对产品设计目录下的文档进行直接增删改。
- **例外**：在「4.1.5 主会话输出交付总结」步骤中，主会话可撰写并保存「交付总结_面向业务与领导」类文档；该文档为归纳与转述，不替代任何 subagent 产出的正式文档。此为**仅此一步**允许主会话直接写文档。

### 2.3 调用方式

调用 subagent 时，统一使用 `Agent` 工具（`subagent_type: "general-purpose"`），将对应 agent 文件的完整内容作为 prompt 前缀，附加任务描述、时间戳、文档路径等上下文。subagent 之间不直接互相调用，通过主会话串联。

## 第三部分：规范约定

> 各角色专属执行细则（原型设计准则、用例格式、问题分析报告结构、PRD 规范等）以对应 agent 文件为权威来源，本部分仅维护跨角色的全局规范。

### 3.1 目录与命名规则

#### 3.1.1 产品需求入口目录

- 路径：`产品设计/产品需求/模块/模块_需求名/`（如 `产品设计/产品需求/SOP/SOP_计划结果-计划指标前端重构/`）
- 用途：仅存放需求入口材料（`需求.txt`、业务方原始描述、截图、附件等）
- **禁止**：在该目录内存放正式 PRD、用例、审核报告等文档

#### 3.1.2 产品 PRD 目录

- 路径：`产品设计/产品PRD/模块/模块_需求名/`
- 用途：需求维度的总入口目录；用例文件与 PRD 存放于同一时间戳子目录
- **禁止**：通过修改目录名（追加 `_v2`、日期后缀等）来区分多次迭代
- 版本管理：必须采用「时间戳子目录 + 功能历史」方式（见 3.1.7）

#### 3.1.3 产品原型图目录

- 路径：`产品设计/产品原型图/模块/模块_需求名/`
- 要求：HTML 原型与 `设计说明.md` 必须按时间戳子目录分批次存放，严禁在同一份原型文件上堆叠多轮大改

#### 3.1.4 产品用例目录

- 默认与 PRD 同目录：存放在 `产品设计/产品PRD/模块/模块_需求名/时间戳/` 下
- 文件命名：`模块_需求名_用例.md`
- **禁止**：将不同迭代的用例混写在同一文件中；每一轮迭代的用例须放在本轮的时间戳子目录中

#### 3.1.5 产品审核目录

- 路径：`产品设计/产品审核/模块/模块_需求名/`
- 用途：存放 product-reviewer 输出的审核报告，按时间戳子目录管理
- 由 product-manager 在需求分析初期预创建（与 PRD、原型图目录同时建立）

#### 3.1.6 产品问题分析目录

- 路径：`产品设计/产品问题分析/模块/模块_BUG_yy-mm-dd_xx/`（如 `SOP_BUG_2026-03-03_01`）
- 用途：存放问题分析报告及其附属材料
- 建档规则见 product-test-manager.md

#### 3.1.7 时间戳子目录与功能历史（强制规范）

适用于：`产品需求`、`产品PRD`、`产品原型图`、`产品审核` 下的 `模块/模块_需求名/` 目录。

| 项目 | 规则 |
|------|------|
| 目录层级 | 第一层为「模块名」，第二层为「模块_需求名」或「模块_BUG_yy-mm-dd_xx」 |
| 版本管理 | 禁止直接堆叠多版本文件；须存在 `功能历史.md`，所有具体产物一律存放在以时间戳命名的二级子目录中 |
| 时间戳格式 | 14 位纯数字 `yyyyMMddHHmmss`（如 `20260303103045`） |
| 时间取值 | 本次需求任务在主会话中启动时的时间点；同一轮 PRD→原型→用例→审核 使用**完全相同的时间戳** |
| 功能历史 | 每次新增时间戳子目录时，必须同步更新 `功能历史.md`，写清时间戳、本轮目的、与上一轮差异 |
| 时间戳传递 | 由主会话生成一次，显式传入所有 subagent；独立工作模式下各 agent 的时间戳处理规则见对应 agent 文件 |

**严禁行为**：在同一时间戳目录中混写两轮不同方案；在旧文件尾部追加新一轮内容而不新建时间戳子目录；通过修改「模块_需求名」目录名规避规则。

**历史不规范目录**：一律视为「历史遗留，仅供只读参考」，不得在其中继续写入；新一轮迭代只能在符合规则的新时间戳子目录中写入。

#### 3.1.8 产品知识库目录（特殊规则）

- 路径：`产品设计/产品知识库/模块/类别（代码、数据库等）/...`；竞品知识库位于 `产品设计/产品知识库/竞品/`（目录结构与 README 规范见 `.claude/skills/prd-writing/SKILL.md` 第 2.3 节）
- **不适用**时间戳子目录规则；知识库文档以「始终保持最新、可被覆盖更新」为目标
- 更新时应在文档内注明「更新时间」与「本次调研范围」
- **严禁**在知识库目录下使用与 PRD 相同的时间戳子目录结构

#### 3.1.9 模块目录命名统一规则

| 模块 | 统一使用 | 禁止使用 |
|------|----------|----------|
| S&OP | SOP | S&OP |
| AMS | AMS | SCH |
| 其它 | MDS、SDS、IPS、MRP、MPS、DFP | 不得混用 |

若未来新增模块，须先在本规则中补充模块编码后，方可在 `产品设计/产品XXX/模块` 创建对应目录。

### 3.2 文档流转与对话输出规则

| 规则 | 说明 |
|------|------|
| 文档是唯一完整载体 | 所有详细内容须写入对应 Markdown 文档；对话回复只允许包含简明摘要（3～10 条）、关键文档路径、待决策点/下一步提示；严禁在对话中复制大段文档正文 |
| 各角色输出长度控制 | product-manager：现状/限制/风险摘要 + 知识库路径 + PRD 路径 + 关键点摘要 + 待决策清单；product-frontend-designer：原型路径 + 设计说明路径 + 设计要点；product-test-manager：用例路径 + 覆盖场景摘要 + 疑问点；product-reviewer：审核报告路径 + 审核结论摘要 + 下一步建议 |
| 禁止双维护 | 任一信息点只能在文档中完整维护一次；更新须先改 MD 文档，再在对话中给出新摘要与路径 |
| 引用文档方式 | 须给出相对路径；指向某轮迭代时须标明时间戳目录名 |

## 第四部分：工作流流程

每个步骤统一结构：**前置条件 → 流程 → 产出物 → 流程守卫 / 阶段确认**。

### 4.1 正向需求流程（需求 → PRD → 原型 → 用例 → 审核）

#### 4.1.1 需求提出、现状调研与 PRD 撰写（product-manager）

**前置条件**：用户以自然语言描述业务需求，并指定需求入口目录或提供需求说明。

**流程**：
- 主会话读取需求入口目录（如有 `需求.txt` 等材料），整理所属模块、功能范围、代码来源、是否需要原型等上下文后调用 product-manager。
- product-manager 按序完成：① 现状调研（代码 + 数据库，结果沉淀到知识库）；② PRD 撰写（存入 `产品设计/产品PRD/模块/模块_需求名/时间戳/`）；③ 预创建同名协同目录（`产品原型图/`、`产品审核/` 对应路径）。
- 主会话向用户转达：PRD 路径、调研摘要与限制点、**关键待决策点列表**，请用户逐项给出决策或暂缓。

**产出物**：PRD 文件、知识库更新（代码/数据库调研结果）、各协同目录预建。

**流程守卫 / 阶段确认**：
- 用户须以明确同意语（如「同意按此 PRD 推进后续原型/用例」）确认方可继续；仅说「继续」不视为签收。
- 在未收到上述确认前，主会话禁止调用 product-frontend-designer、product-test-manager 或 product-reviewer。

---

#### 4.1.2 原型设计（product-frontend-designer）

**前置条件**：4.1.1 用户已签收 PRD。

**流程**：主会话调用 product-frontend-designer，传入 PRD 路径、时间戳、原型存放目录。product-frontend-designer 在 `产品设计/产品原型图/模块/模块_需求名/时间戳/` 下生成 HTML 原型 + `设计说明.md`。

**可跳过规则**：若需求为纯后端/架构/代码优化类（不新增前端页面、不涉及复杂交互），须满足以下任一条件方可跳过，直接进入 4.1.3：
- 产品经理向用户发起硬确认「疑似不需要前端页面，是否跳过原型设计？」，用户回答【是】或【跳过】；
- 需求文档中已明确「该需求不需要前端设计」。

**产出物**：HTML 原型文件、`设计说明.md`。

**流程守卫 / 阶段确认**：
- 若用户在原型阶段提出「需先调整 PRD」，须回到 4.1.1，由产品经理更新 PRD 并再次获得确认。
- 主会话提示用户检查 PRD + 原型，询问「是否同意按当前 PRD+原型进入用例阶段」。仅当用户使用明确同意语时，才允许调用 product-test-manager。

---

#### 4.1.3 用户用例 / 测试用例（product-test-manager）

**前置条件**：4.1.1 已完成且签收，4.1.2 已完成（或已按可跳过规则跳过）。

**流程**：主会话调用 product-test-manager，传入 PRD 路径、原型路径（如有）、时间戳。product-test-manager 生成独立用例文件（`模块_需求名_用例.md`，存入 PRD 同时间戳目录），并将 PRD 的用例章节改为简洁引用。

**产出物**：独立用例文件、PRD 用例章节更新。

**流程守卫 / 阶段确认**：
- 主会话提示用户检查 PRD、原型、用例是否对齐，询问「是否同意进入设计审核阶段」。仅当用户使用明确同意语时，才允许调用 product-reviewer。

---

#### 4.1.4 设计审核与对标（product-reviewer）

**前置条件**：4.1.1～4.1.3 已完成且签收。

**流程**：主会话调用 product-reviewer，传入功能名、时间戳、PRD 路径、原型路径。product-reviewer 在 `产品设计/产品审核/模块/模块_需求名/时间戳/` 下输出审核报告。

**产出物**：审核报告（含背景、目标、现状、问题、竞品对标、改进建议、「用户意见」、审核结论）。

**流程守卫 / 阶段确认**：
- 主会话仅提示用户阅读审核报告并在「用户意见」中给出反馈；等待用户表态「按当前方案进入开发」或「先按审核意见修订 PRD/原型/用例」。
- 未收到明确结论前，AI 不得主动延伸「开发任务拆解」「实现方案细化」等额外任务。

---

#### 4.1.5 主会话输出交付总结（主会话）

**前置条件**：4.1.4 已完成，用户已阅读审核报告并给出「认可」或「需修订」表态。

**流程**：主会话撰写「交付总结_面向业务与领导」，分类分点说明改造内容与期望效果（每类 1～2 个典型例子），存入 PRD 同时间戳目录（`产品设计/产品PRD/模块/模块_需求名/时间戳/交付总结_面向业务与领导.md`）。

**产出物**：`交付总结_面向业务与领导.md`。此为**唯一**允许主会话直接写文档的步骤。

**流程收尾**：交付总结输出后，正向需求 4.1.1～4.1.5 闭环结束。

---

### 4.2 问题驱动流程（问题 → 分析 → 改进需求）

#### 4.2.1 问题收集与分析

**前置条件**：用户提供自然语言问题描述，或指向 `产品设计/产品问题分析/模块/模块_BUG_yy-mm-dd_xx/` 下已有目录路径。

**流程**：
- 主会话调用 product-manager 对相关代码与数据库进行调研，将结论沉淀到知识库。
- 主会话再调用 product-test-manager 基于知识库与问题描述完成问题分析报告。
- 建档询问与目录创建规则见 product-test-manager.md。

**产出物**：问题分析报告（现状 / 问题 / 解决方案三大章节）、知识库更新。

**流程守卫**：问题分析阶段不得直接改 PRD 或调用 product-frontend-designer；须等用户在 4.2.2 明确确认后方可考虑发起增量需求。

---

#### 4.2.2 用户确认（是否升级为需求的决策点）

**前置条件**：4.2.1 问题分析报告初稿完成。

**流程**：主会话提醒用户打开问题分析报告，确认现状/问题/解决方案是否准确，明确询问「是否同意按该问题分析作为后续改进依据」。若用户认为不充分，product-test-manager 根据新说明修订报告，直至用户确认。

**流程守卫 / 阶段确认**：仅当用户明确表示「同意按该问题分析作为改进依据」时，才允许进入 4.2.3；单纯的「继续」「下一步」不视为签收。

---

#### 4.2.3 从问题到增量需求（进入正向流程的唯一通道）

**前置条件**：4.2.2 用户已签收问题分析报告。

**流程**：主会话调用 product-manager，基于问题分析报告发起改进需求：在 `产品设计/产品需求/模块/` 下创建 `模块_问题xxx改进` 入口目录；在 `产品设计/产品PRD/模块/` 下新建目录，以问题分析报告为输入撰写正式增量 PRD（PRD 中显式引用报告路径）；后续完整执行 4.1 正向需求流程（4.1.1～4.1.5）。

**流程守卫**：若用户撤回或修改对问题分析报告的认可，须先更新报告并再次获得确认，方可发起或调整增量需求。问题改进需求必须重新完整执行 4.1 正向工作流，不得跳过任何用户确认节点。
